Misión 1 · The Intern's Token

Menor privilegio y restricciones DDL

Recursos de estudio

Principio de menor privilegio (PoLP): cada usuario o servicio recibe solo los permisos indispensables para su labor. Si su credencial se compromete, el daño queda limitado (menor radio de explosión).

NOT NULL impide valores nulos en una columna. UNIQUE impide valores repetidos. Ejemplo: email TEXT NOT NULL UNIQUE.

Dato de SQLite: no permite ALTER TABLE ... ADD CONSTRAINT. Para añadir restricciones se reconstruye la tabla: crear la nueva, copiar los datos, borrar la vieja y renombrar.

Preguntas guía

1. ¿Qué dos campos de permisos tiene intern_04 que no debería tener?
Ejecuta audit perms. Fíjate en es_admin y puede_leer_vip. ¿Qué sentencia modifica filas existentes? Recuerda filtrar con WHERE o cambiarás a todos.
2. ¿Puedes agregar UNIQUE con un simple ALTER TABLE?
No en SQLite. Piensa en el proceso de cuatro pasos: crear tabla nueva con las restricciones, copiar, borrar la original, renombrar.
3. ¿Por qué falla la copia si copias todo tal cual?
Ejecuta audit schema. Hay emails duplicados y nulos en los datos actuales. La tabla nueva los rechazará, así que debes depurarlos al copiar (por ejemplo, conservar un solo registro por email y asignar un correo a quienes no tienen).
Revelar solución

%% Comando 1.
UPDATE permisos_usuarios SET es_admin=0, puede_leer_vip=0 WHERE usuario='intern_04';

%% Comando 2.
CREATE TABLE empleados_new(id INTEGER PRIMARY KEY, nombre TEXT,
  email TEXT NOT NULL UNIQUE, rol TEXT);

%% Comando 3:
INSERT INTO empleados_new(id,nombre,email,rol)
SELECT id, nombre, COALESCE(email, lower(nombre)||'@corp.com'), rol
FROM empleados
WHERE email IS NULL
   OR id IN (SELECT MIN(id) FROM empleados WHERE email IS NOT NULL GROUP BY email);

%% Comando 4:
DROP TABLE empleados;

%% Comando 5:
ALTER TABLE empleados_new RENAME TO empleados;

Después ejecuta commit-incident. Escribe cada bloque en una sola línea con sql delante.

Por qué funciona: el UPDATE aplica PoLP; COALESCE rellena los nulos; el MIN(id) elimina duplicados. En un caso real, borrar a "Ana Ruiz" sería una decisión de negocio: quizá corresponda corregir su email en lugar de descartarla.

Misión 2 · Ghost Invoices

Claves foráneas e integridad referencial

Recursos de estudio

Llave foránea (FK): columna que apunta a la llave primaria de otra tabla y crea un vínculo relacional.

Integridad referencial: ninguna FK puede apuntar a un dato inexistente.

Reglas de cascada: RESTRICT impide borrar o actualizar al padre si tiene hijos; CASCADE propaga el cambio; SET NULL pone la FK del hijo en NULL.

Huérfano: fila hija cuya FK no coincide con ningún padre. Se detecta con un LEFT JOIN y IS NULL.

Preguntas guía

1. ¿Cómo encuentras las facturas sin usuario?
Ejecuta audit orphans. Verás las facturas con id_usuario 99 y 404. ¿Las borras o las reasignas? Ambas opciones son válidas; borrar es lo más simple aquí.
2. ¿Puedes agregar la FK a la tabla existente?
No en SQLite. Reconstruye facturas con la cláusula FOREIGN KEY (...) REFERENCES ... ON DELETE ....
3. ¿Cuál regla de cascada evita borrar un usuario con facturas?
La que "restringe" la operación. Comprueba luego con audit fk y con un DELETE real.
Revelar solución
DELETE FROM facturas
WHERE id_usuario NOT IN (SELECT id_usuario FROM usuarios);

CREATE TABLE facturas_new(
  id_factura INTEGER PRIMARY KEY,
  id_usuario INTEGER NOT NULL,
  monto REAL,
  FOREIGN KEY (id_usuario) REFERENCES usuarios(id_usuario) ON DELETE RESTRICT);

INSERT INTO facturas_new SELECT * FROM facturas;
DROP TABLE facturas;
ALTER TABLE facturas_new RENAME TO facturas;

Prueba: sql DELETE FROM usuarios WHERE id_usuario=1 debe fallar con "FOREIGN KEY constraint failed". Luego commit-incident.

Alternativa: en vez de borrar, crea un usuario "Desconocido" y reasigna las facturas con UPDATE para conservar el rastro contable. El juego acepta ambas.

Misión 3 · The Monolith Freeze

Normalización 1NF a 3NF e indexación

Recursos de estudio

1NF: valores atómicos, sin listas en una celda. 'Laptop;Mouse' las viola.

2NF y 3NF: cada atributo depende de la clave y solo de ella. El nombre, email y ciudad del cliente dependen del cliente, no del pedido; por eso van en su propia tabla.

Tabla de detalle (o pivote): guarda una fila por cada producto de un pedido, enlazada por FK.

Índice: estructura (B-tree) que evita el Full Table Scan. En EXPLAIN QUERY PLAN, SCAN es recorrido completo y SEARCH ... USING INDEX es búsqueda indexada.

Preguntas guía

1. ¿Qué entidades se mezclan en la tabla monolito?
Clientes, pedidos y productos por pedido. Tres entidades, tres tablas: clientes, pedidos, detalle_pedidos.
2. ¿Cómo sacas los clientes sin repetirlos?
SELECT DISTINCT sobre las columnas del cliente. Luego, para enlazar pedidos, une por un campo estable como el email.
3. ¿Cómo separas 'A;B;C' en filas?
SQLite no tiene función split. Usa un CTE recursivo con instr y substr: toma el texto antes del primer ';' y continúa con el resto. Añadir un ';' al final simplifica el caso de la última palabra.
4. ¿Sobre qué columna debe ir el índice y cómo lo verificas?
Sobre pedidos(fecha_pedido). Ejecuta audit plan antes y después: debe cambiar de SCAN a SEARCH ... USING INDEX.
Revelar solución
CREATE TABLE clientes(id INTEGER PRIMARY KEY, nombre TEXT, email TEXT UNIQUE, ciudad TEXT);
INSERT INTO clientes(nombre,email,ciudad)
  SELECT DISTINCT cliente_nombre, cliente_email, cliente_ciudad FROM monolito;

CREATE TABLE pedidos(id_pedido INTEGER PRIMARY KEY,
  id_cliente INTEGER REFERENCES clientes(id), fecha_pedido TEXT, total REAL);
INSERT INTO pedidos
  SELECT m.id_pedido, c.id, m.fecha_pedido, m.total
  FROM monolito m JOIN clientes c ON c.email = m.cliente_email;

CREATE TABLE detalle_pedidos(id_detalle INTEGER PRIMARY KEY,
  id_pedido INTEGER REFERENCES pedidos(id_pedido), producto TEXT);
WITH RECURSIVE s(id,item,rest) AS (
  SELECT id_pedido, '', productos||';' FROM monolito
  UNION ALL
  SELECT id, substr(rest,1,instr(rest,';')-1), substr(rest,instr(rest,';')+1)
  FROM s WHERE rest <> '')
INSERT INTO detalle_pedidos(id_pedido,producto)
  SELECT id, item FROM s WHERE item <> '';

CREATE INDEX idx_pedidos_fecha ON pedidos(fecha_pedido);
DROP TABLE monolito;

Por qué funciona: cada hecho vive en un solo lugar (3NF), los productos son atómicos (1NF) y la búsqueda por fecha usa el índice en lugar de recorrer toda la tabla. Ejecuta commit-incident al terminar.
